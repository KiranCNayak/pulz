# Decisions Log — Pulz

Quick-reference list of decisions already made and closed during design.
If you're an agent or contributor picking this up: **treat these as
settled** — don't relitigate them without a new, explicit instruction from
the project owner. Each entry says what was decided and why, so you can
tell a "settled trade-off" apart from an "open question" (see
`ARCHITECTURE.md` §8 and `DESIGN.md` §8 for what's still genuinely open).

| # | Decision | Why | Where detailed |
|---|---|---|---|
| 1 | Scoring is **time-bracket based**, not rank-based | Rank-based scoring needs a strict global ordering of near-simultaneous answers across variable network latency — race-condition-prone. Time-bracket scoring only needs each player's own elapsed time. | PRD §5 |
| 2 | Scoring buckets are 5 tiers at 20%-of-time-limit steps, multiples of a base-10 point value, always non-negative integers | Explicit requirement: no fractional/negative scores, no "ugly" point values like 10 vs 25. | PRD §5, DESIGN.md §5 |
| 3 | Default question time limit: 20 seconds, configurable 5–120s per question | Matches an industry-validated default (Kahoot! itself defaults to 20s); configurable so text-heavy questions aren't shortchanged. | PRD §4.1 |
| 4 | No native mobile app for MVP | Responsive web covers "play from any device" without app-store overhead. | PRD §2, §7 |
| 5 | Host is split into two views: **Controller** (interactive) and **Display** (cast-friendly, read-only) | Matches real usage (host laptop + projected shared screen); both are just different subscriptions to the same event stream, not separate backend concepts. | PRD §4.2, DESIGN.md §6 |
| 6 | Question and answer-option order are randomized **per session**, not per player | Shared-screen "look at the shape" gameplay requires everyone in a session to see the same order. | DESIGN.md §4 |
| 7 | Podium (top 3, gold/silver/bronze, confetti/animation) is in MVP, not deferred | Low implementation cost (presentation-layer only), high payoff for the "aha" moment. | PRD §4.4 |
| 8 | Players see only their **own rank** (`"X of Y"`), never the full leaderboard | Explicit scope reduction: smaller per-player payload, avoids exposing other players' standings. | PRD §6, DESIGN.md §3 |
| 9 | No login for Host or Player/Spectator — only **Creators** have accounts | Keeps the common-case flow (join and play) frictionless. | PRD §3 |
| 10 | Join model: internal session UUID + short **6-character alphanumeric** join code | UUID is the unguessable "real" identifier (used for the results link); the short code is what a human actually types. Raised from an initial 4-character design (~1.68M combinations, brute-forceable in seconds) to 6 characters (~2.18 billion combinations) once the always-on/no-auth abuse-resilience requirement surfaced. | PRD §4.2, §8 |
| 11 | Pre-start joiners become **Players**; post-start joiners default to **Spectators** | Prevents a late joiner from disrupting an in-progress question, while still letting them watch. | PRD §4.3 |
| 12 | Spectator → Player promotion requires **explicit per-request Host approval**; no bulk-approve in MVP | Simpler to build and reason about; bulk approve is a listed post-MVP nice-to-have. | PRD §4.3, §9 |
| 13 | Promoted spectators do **not** get retroactive points for questions missed while spectating | Avoids retroactive score recomputation complexity. | PRD §4.3 |
| 14 | Results snapshot is ephemeral with a **configurable TTL, default 24h** | Explicit requirement to minimize storage cost/duration; default chosen as a reasonable "long enough to share, short enough to not accumulate." | PRD §4.4, §9 |
| 15 | TTL cleanup implemented as an **in-process interval sweep**, not a separate cron/scheduled service | Zero additional infrastructure; read path also defensively filters on `expires_at` so correctness never depends on the sweep's timing. | ARCHITECTURE.md §3 |
| 16 | Live `GameSession`/`Participant`/`Answer` state lives **in server process memory**, not the DB, while a game is in progress | Cheapest and fastest option at MVP scale; accepted trade-off is state loss on server restart mid-game. | ARCHITECTURE.md §2 |
| 17 | Backend: Node.js + TypeScript, Fastify (REST) + Socket.IO (realtime, rooms = sessions) | Rooms map directly onto sessions; Socket.IO's built-in reconnect/backoff covers the "phone drops mid-question" requirement without hand-rolling it. | ARCHITECTURE.md §1 |
| 18 | No horizontal scaling / multi-instance session routing in MVP | Would require moving session state out of process memory (e.g. to Redis) and adding sticky routing — real infra cost the PRD asked to avoid; revisit only if actually needed. | ARCHITECTURE.md §8 |
| 19 | Direct pushes to `main`, no PR-gated workflow, for this phase | Explicit project-owner instruction; revisit if the contributor pool grows beyond one. | This doc |
| 20 | Project name: **Pulz** | Chosen by project owner; merges "pulse" (real-time/speed scoring) and "quiz." | — |
| 21 | No blanket per-IP bans for abuse response; abuse handling is **temporary and composite-key-scoped** (IP + lightweight client id), not a persistent IP blacklist | IPs are shared (NAT/school Wi-Fi/CGNAT) and trivially rotated by an actual attacker — a blanket ban both over-punishes innocent shared-IP users and under-deters a real attacker. | PRD §8, ARCHITECTURE.md §11 |
| 22 | Anonymous-abuse hardening is scoped to **join / WebSocket connect / in-game messages only**, not session creation | Session creation already requires an authenticated Creator (Decision #9), so it's not part of the anonymous attack surface. | PRD §8, DESIGN.md §8 |
| 23 | Join-code brute-forcing is defeated by a **per-code failed-attempt lockout** (temporary), independent of and in addition to the 6-character length increase (#10) | Length alone only raises the cost of a blind guess; a targeted attacker hammering one known-active code still needs to be stopped directly. | DESIGN.md §8 |
| 24 | Edge/DDoS protection via **Cloudflare free tier** in front of both frontend and backend, with conditional Turnstile challenges (not shown to every user) | Outsources L3/L4 DDoS absorption to infrastructure built for it, at zero cost, without adding friction to the common case of a legitimate player joining. | ARCHITECTURE.md §11 |
| 25 | ORM/query layer: **Prisma** | Lightweight, TypeScript-first, generates types from schema (matches "one language, minimal moving parts" theme in ARCHITECTURE.md §1), and its migration model gives a durable, reviewable history for the durable entities (Creator/Quiz/Question/Option/ResultsSnapshot) without hand-rolling SQL migrations end to end. Trade-off accepted: Prisma's schema language has no native `@@check`/numeric-CHECK syntax, so the `time_limit_seconds` range constraint and the "at most one correct option" partial unique index are hand-added in the migration SQL rather than expressed in `schema.prisma` itself — documented inline in both files so it isn't lost on the next `prisma migrate dev`. | backend/prisma/schema.prisma, backend/prisma/migrations/0001_init/migration.sql |
| 26 | Backend lives in a top-level **`backend/`** directory (monorepo-by-convention, not a workspace tool) | Mirrors ARCHITECTURE.md §4's split frontend/backend deploys — a sibling `frontend/` will hold the React+Vite SPA (step 2) with its own independent deploy, without needing npm/pnpm workspaces machinery for what's currently a two-package repo. | This doc, ARCHITECTURE.md §4-§5 |
| 27 | `src/` split into `routes/` (Fastify HTTP handlers + JSON schemas), `sockets/` (Socket.IO handlers), `services/` (business logic incl. validation), `db/` (Prisma client + TTL sweep), `domain/` (shared constants), `types/` (request/response DTOs) | Keeps the "validation is server-authoritative" and "exactly-one-correct-option" invariants (CLAUDE.md, DESIGN.md §1) in one reusable service layer rather than duplicated across REST handlers and (later) socket handlers. | backend/src/ |
| 28 | Creator identity for the quiz-CRUD REST endpoints is currently a placeholder **`x-creator-id` request header**, not real auth | ARCHITECTURE.md §7's email/password (or JWT) Creator auth hasn't been built yet; rather than leave ownership scoping unimplemented (and every quiz effectively public/unscoped) until auth lands, the CRUD layer already takes and enforces a creator id, just from a stand-in header. **Must be replaced** with session/JWT-derived identity before this leaves scaffolding — tracked as follow-up work, not a scope decision to keep. | backend/src/routes/quiz.route.ts |
| 29 | "Exactly one correct option per question" enforced at the **application layer** (service-layer check on every create/update), with a **partial unique index** (`WHERE is_correct = true`) as a DB-level backstop against "more than one" | Matches DESIGN.md §1's explicit guidance ("app-level check on write; consider a partial unique index"). The partial unique index alone can't guarantee "at least one," so the app-layer check remains authoritative for the full invariant. | DESIGN.md §1, backend/src/services/quiz.service.ts |
| 30 | Question `time_limit_seconds` clamped to `[5, 120]` both in the application layer (on every write) and via a DB `CHECK` constraint | Belt-and-suspenders per the task's validation requirements: the app clamps rather than rejects (so a slightly-out-of-range value from a client just gets pulled into range instead of failing the whole request), while the DB CHECK guarantees the invariant holds even for a write that bypasses the app layer. | PRD §4.1, backend/prisma/migrations/0001_init/migration.sql || 31 | Start a **parallel, non-shipping `backend-go/` module** to measure Go vs. Node performance for this workload | Owner-driven curiosity about real performance gains; explicitly not a migration plan, not scheduled against MVP work, doesn't block frontend/other MVP steps. Stack: `chi` router, `pgx`+`sqlc` for DB (no ORM, to avoid confounding the perf measurement), `hey` for load testing — all installed as user-scoped `go install` tools, nothing system-wide. | `docs/GO_V2_EXPLORATION.md`, PRD §10 |
